## 4. 上次 review 原文

## 审查发现

1. **[P1] 读取旧记忆时的 ID 回填没有工作区锁，可能覆盖并发写入。**
   `readDetailed()` 会直接调用 `ensureIdentity()` 写盘，见 `src/dao/memory-store.ts:253`、`src/dao/memory-store.ts:278`。如果进程 A 正在回填，进程 B 同时通过 `remember` 写入新正文，A 随后可能在 `src/dao/memory-store.ts:1034` 将旧正文重新写回。`src/dao/memory-store.ts:994` 的 hash 检查与最终写入之间仍有竞争窗口，而且 `persistIdentity()` 的失败返回值在 `src/dao/memory-store.ts:962` 被忽略。回填也应进入同一工作区锁，并在失败时重新读取或报告冲突。

2. **[P1] 部分搜索的游标会重复结果，遇到 oversized session 时永远无法推进。**
   超出字节预算后，`src/context/wire-context.ts:893-900` 设置 `nextCursor` 却使用 `continue` 扫描后续 session。恢复时又从第一个未完成 session 开始，导致后续 session 被重复扫描；若该 session 单独就超过预算，每页都会返回相同 `nextCursor`。
   已复现：第一页和恢复页都返回 `session_small`，两页的 `nextCursor` 都为 `session_big`。这里需要保持游标顺序语义，或对单文件超预算返回明确、可处理的终止状态。

3. **[P1] 主题时间线忽略 `deleted/orphaned` 状态和稳定 ID，会展示无关的新记忆。**
   `src/vis/api.ts:163-180` 仍直接按缓存的 `folder/key` 读取文件，`src/vis/api.ts:213-215` 没有检查引用状态或文件 ID。
   已复现：删除记忆 A 后，在同路径创建记忆 B，旧主题引用虽然为 `deleted`，时间线却返回了 B 的完整正文。这不仅违反引用完整性，也可能把无关内容错误注入主题上下文。

4. **[P1] 递归删除文件夹仍绕过回收站和 journal，属于永久删除。**
   `src/vis/api.ts:680-692` 直接执行 `fs.rmSync(..., { recursive: true })`，没有逐条调用软删除，也没有写入恢复日志。单条 `delete_memory` 已支持 trash/restore，但文件夹删除会永久丢失其中全部记忆，当前软删除实现尚不完整。

5. **[P1] 移动记忆时源文件删除失败会被静默忽略。**
   `src/dao/memory-store.ts:667-673` 先写目标文件，再捕获并忽略源文件 `unlink` 失败，随后仍返回成功。结果是源、目标同时存在且共享同一个稳定 ID；后续 journal 还会提交该操作。Windows 文件占用或移动中途崩溃都可能触发该状态，而当前 journal 恢复只重建派生数据，不能消除重复权威文件。

6. **[P1] 仪表盘 singleton 的跨进程竞争仍未闭合。**
   `src/vis/auto-start.ts:197-207` 的“读取 runtime → 写入 claim”不是原子操作，两个进程可以同时认为自己拥有实例。先拥有者退出时，`src/vis/auto-start.ts:442-480` 又不检查当前 runtime 的 PID/token 就删除文件，可能删掉后拥有者的运行记录。
   现有并发测试 `tests/vis.test.ts:704-713` 只是在同一进程内 `Promise.all`，会共享 `pendingStart`，覆盖不到这个真实跨进程窗口。该竞争由控制流确认，未做跨进程实测。

7. **[P2] 仪表盘新建文件没有 CAS 保护。**
   `src/vis/static/app.js:1227-1233` 对新文件发送 `expectedRevision: undefined`。两个客户端同时新建同 key 文件时，即使请求被工作区锁串行化，后写者仍会覆盖先写者，而不会收到冲突。新建场景应携带“期望不存在”的约束，例如 `expectedRevision: 0`。

8. **[P2] 仪表盘 essence 保存没有写 journal，与注释和 changelog 不符。**
   `src/vis/api.ts:697-704` 声称 essence 已 journaled，但实际 `storeEssenceContent()` 在 `src/tools/system-tools.ts:703-753` 只有锁、写文件和索引更新，没有 prepare/commit。已验证保存后 journal 条目数为 `0`。在正文写入后、索引更新前崩溃时，不会留下恢复记录。

9. **[P2] purge 报告会错误地显示剩余 host wire 为 0。**
   `src/purge.ts:128-133` 使用 memory store 的 `workspace-*` 目录名去查找宿主的 `wd_*`/`wm_*` session 目录，两者并不对应。已复现：实际发现 1 个 wire，`hostWireSessions` 报告为 0。这里应复用 `src/maintenance.ts:350-358` 的会话发现逻辑，否则清除报告的残留范围不可信。
