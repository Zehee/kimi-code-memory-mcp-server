## 7. 逐项复现记录

复现脚本在 `reviews/repro-2026-11-23/`，每个脚本的证据来源见同目录 `README.md`。在仓库根目录运行 `npx tsx reviews/repro-2026-11-23/<脚本>`；脚本内 `REPO` 是本机绝对路径。

### U-01（P1）进行中的 turn 永久冻结

**机制**：host 在 turn 开始时就把 `turn.prompt` 写入 wire，agent 的 `content.part` / `tool.call` 在之后陆续追加。tick 落在 turn 进行中时，这个 turn 立刻被精炼成「只有用户提问」的行；turn 完成后它的 id 已在 `existing` 里，被 `missing` 过滤掉，不再重写。判断一行是否过期的行级 `source_content_hash` 从未计算（`src/refine/adapter.ts:82` 恒为 `null`）。

**源码复现**（`ws1-bg.mts` S1）：

```text
row 0 after tick DURING the turn: summary="how do I fix the flaky lock test" facts=[] files=[] tools=[]
turn completed -> next tick refined 0 turn(s); lag gauge = 0
row 0 AFTER the turn completed: summary="how do I fix the flaky lock test" facts=[] files=[] tools=[]
refined search "isLockStale": 0 match(es)
(wire turn 0 agentText starts with: "Implemented death detection in t")
```

**会不会被别的路径修好**：不会。`search_context` 的内联精炼同样 `if (existingIds.has(m.turnId)) continue;`（`context-tools.ts:466`）。仓库里唯一会无条件覆盖已有行的是 `tag_theme`（`theme-tools.ts:212-219`），只作用于被显式打标签的 turn。

**host wire 上的命中率**（来源 B，`selfaudit-stats.mts`，只统计索引器能看到的 19 个主 agent wire；已确认正在写入的那个 wire 在发现列表里，`selfaudit-discovery.mts`）：

- 172 个可测时长的 turn：中位数 102 秒，p90 516 秒，**68% 超过 60 秒的 tick 间隔**，94.8% 超过 10 秒。
- 每个 turn 的 `turn.prompt` 之后到 `turn.ended` 之间有 30～110 行事件，提示词确实先于回答落盘（`probe-wire4.mjs`）。
- 若 tick 相位均匀，被冻结的期望比例约 84%。

**为什么现在没被察觉**：交互式搜索对已扫描的会话以 wire 为准（`DEFAULT_MAX_SCAN_BYTES` = 32 MiB），冻结的行被原始结果盖住了。本工作区主 agent wire 共 22.1 MiB，离预算不远；超过后未扫描的会话走 refined-only，冻结行会直接浮出来。`/api/refined-turn/...` 与 `/api/searches/:key` 展示的也是这些半成品。同时 lag 指标报 0。

**建议修复**：按目标文档实现行级 `source_content_hash`——对解析出的 `WireTurn` 规范化后哈希，写入 `refined_turns.source_content_hash`；批处理时 `todo` 取「不存在**或**行哈希 ≠ 当前来源哈希」的 turn。在途、追加、改写三种情况一次覆盖，U-02 也顺带解决大半。

### U-02（P2）wire 变小或改写时不作废重建

目标文档规则：「wire 变小或身份变化：该 session 索引作废并重建」。实现里没有任何缩小或身份变化的检测；`wireIdentity` 实际是 `JSON.stringify({ refinedCount })`，不是 wire 的身份。

**复现**（`ws1-freshness.mts` 上半）：

```text
wire shrank 4 -> 2 turns; next batch call refined 0 turn(s)
-> row for turn 1 describes the OLD turn 1 while the wire now says "REWOUND question 1"; rows 2-3 are orphaned: yes
-> refined search for vanished content "topic3": 1 match(es)
```

turn id 是文件内的位置序号，wire 一旦被回退重写，同一个 id 对应的就是另一段对话。触发前提（host 回退重写 wire）本轮没有观察到，判定依据是目标文档明文要求加上合成复现。

**建议修复**：进度表记录真实的 wire 身份（如首 N 行的哈希）；检测到 `size < lastSize` 或身份变化时，删除该 session 的全部行后在预算内重建。

### U-03（P2）extractor 版本变化不重建，检查点反而盖章

**复现**（`ws1-freshness.mts` 下半）：

```text
extractor version changed 0 -> 1; background call refined 0 turn(s)
rows by extractor_version afterwards: [{"v":"0","c":4}]  (checkpoint says: 1)
```

版本检查没命中时不会跳过，但 `missing` 仍为空，于是什么都不做，然后把检查点无条件写成当前版本。旧摘要从此永久豁免。`EXTRACTOR_VERSION` 目前还是 `'1'`，所以是第一次升级 extractor 时才显现的潜伏问题。

**建议修复**：把「行版本 ≠ 当前版本」也纳入 `todo`；只有当该 session 全部行都是当前版本时才把检查点盖成新版本。

### U-04（P2）主动删除的 refined 行下一 tick 复活

`delete_search_view` 的 `deleteRefinedTurns: true` 文案是「useful for purging low-quality refined data」。检查点用 refined 行数做身份，行数一变就判定「有缺失」并补回。

**复现**（`ws1-bg.mts` S2）：`rows after deleteRefinedTurns: 0` → `next tick rebuilt 1 row(s)`。

`tests/storage.test.ts:2222-2224` 把这个行为断言成了期望结果，CHANGELOG 也明写「without preventing deleted rows being rebuilt」——是有意为之，但与另一个功能的文档化用途矛盾。这是需要拍板的设计冲突。

**建议修复**（二选一）：(a) 删除即持久——增加墓碑表，直到该 wire 再次变化才解除；(b) 保留现状，但把工具描述和看板文案改成「移除后后台会自动重建」。

### U-05（P2）wire 行处理器的同类崩溃点

这次更新给 `toIsoTimestamp` 加了 `Number.isFinite` 守卫，但 readline `'line'` 监听器里抛出的异常不进入 Promise 链（`rl.on('error', reject)` 接不到监听器异常），仓库里也没有 `uncaughtException` 处理器，所以是未捕获异常直接退出进程。

**仓库 `dist/server.js` 隔离启动**（`selfaudit-built-crash.mts`，经 MCP stdio 客户端调用）：

```text
wire tail line: null
  control: listTools             -> responded (24 tools); ping after: yes
  bootstrap_workspace            -> FAILED: MCP error -32000: Connection closed; ping after: no
      server stderr: TypeError: Cannot read properties of null (reading 'type')
  search_context                 -> FAILED: MCP error -32000: Connection closed; ping after: no
wire tail line: {"type":"turn.prompt","input":"a plain string",...}
  bootstrap_workspace            -> FAILED: MCP error -32000: Connection closed; ping after: no
      server stderr: TypeError: (event.input || []).filter is not a function
```

对照 wire（无坏行）四个工具全部正常。`AGENTS.md` 规定每个会话开头必须调 `bootstrap_workspace`，所以一条坏行等于该工作区的强制启动协议失败。被解析的 wire 包括：bootstrap 解析的当前会话、搜索和后台 tick 遍历到的全部会话。

host wire 的情况（来源 B）：本工作区的 wire 里没有非对象行；`input` 的形状没有统计。属于低概率高影响。

**建议修复**：行处理器入口加 `if (!event || typeof event !== 'object')` 跳过并计数；`Array.isArray(event.input)` 守卫；并把整个 `'line'` 回调包一层 try/catch → 计数 + 跳过。

### U-06（P2）lag 指标高估约 30 倍，且每 tick 同步读 22 MiB

`measureLag` 用「非空行数 / 3」估算 turn 数。

**host wire 实测**（来源 B，`selfaudit-stats.mts`，按量规同样的读法，只算 19 个主 agent wire）：

```json
{"wiresSeenByIndexer":19,"mibReadPerTick":22.1,"synchronousMs":246,"trueTurns":174,"linesOver3":5197,"overestimateFactor":29.9,"linesPerTurn":89.6}
```

全部精炼完之后指标仍会长期显示数千的「滞后」。读文件发生在 MCP 进程主线程，每 60 秒阻塞约 250ms。

**建议修复**：用精确口径——wire 侧的 turn 数在 `parseWireFile` 时记入进度表，lag 取「wire turn 数 − 已有行数」；至少应把测量移出主线程 tick。

### U-07（P2）跨进程写锁持续占用时主线程阻塞约 29 秒

**这不是本次更新引入的**，是此前 D7 修复（SQLite busy 重试）自带的设计后果：5 次尝试 × 约 5.8 秒同步 `busy_timeout` + `Atomics.wait` 退避。

**复现**（`ws1-lock.mts`）：

```text
threw after 29053ms -> Error (retryable=undefined): database is locked
event-loop heartbeats (10ms timer) observed during the stall: 1
metrics: refined_busy_retry=5 refined_busy_exhausted=1
```

29 秒内事件循环只跳了一次：所有工具调用、取消信号、看板请求全部停摆。触发前提是写锁被持续占用 5 秒以上（同工作区另一个进程在事务中被挂起或休眠，或 Windows 上杀毒/备份软件锁住 `-wal` 文件）。

**建议修复**：`BUSY_RETRY_ATTEMPTS` 降到 2（最坏约 12 秒）；长期方案是把 refined store 放到 worker。

### U-08（P2）后台索引测试测不到真实路径

`tests/storage.test.ts:2169` 的夹具把 `content.part` 的 `turnId` 放在了**外层**，而解析器读的是 `event.event.turnId`。host wire 里 `turnId` 在 `event` 内且是字符串（来源 B，`probe-wire3.mjs`：7865 条事件无一例外）。

**复现**（`ws1-bg.mts` S5）：`parser result: turnCount=1 agentText=""  <- the fixture's answer is never attached`。

所以这个测试只验证了「turn 数量对得上」——这正是 U-01 能全绿通过的原因。另外：夹具每个 turn 恰好 3 行，与 `lines / 3` 的估算完全吻合，U-06 也测不出来；第 12 条声明（看板 reconcile 收窄）没有任何回归测试。

**建议修复**：夹具改成真实形状；补三条回归——「turn 进行中 → 完成后 tick 必须刷新」「wire 回退后旧行被清理」「`/api/health`、`/api/metrics`、`/api/decisions` 不触发 reconcile」。

### U-09（P3）读取已有 turn id 失败被吞

`listRefinedTurnIds` 抛错时 `existing` 被置为空集，整个会话被视为「全缺失」。复现（`ws1-bg.mts` S3）：`saveRefinedTurns was called for turn ids [0,1] (turn 0 already existed)`。`search_context` 里有同样的写法（`context-tools.ts:435-440`）。建议直接向上抛，由 `runTick` 计入 `background_index_errors`。

### U-10（P3）检查点写入绕过 busy 重试

### U-11（P3）一个畸形主题文件拖垮整个主题列表

校验本身是对的，但 `getThemes` 对每个主题调 `loadTheme`，一个抛错整批失败。复现（`ws4-theme-api.mts`）：

```text

reconcileIndex again        : synced=false skipped=false errors=2
```

因为 reconcile 永远带着这个错误，clean checkpoint 永远写不上。建议逐主题 try/catch，列表里以 `{ name, corrupt: true, error }` 返回。

### U-12（P3）导出的两个韧性缺口

- 导出到已有目录不清理：删除 `a.md` 后重新导出，报告显示 `memory:0 file(s)`，目标目录里 `a.md` 仍在。
- 源目录里有目录联接时整体中止：`EPERM: operation not permitted, copyfile`。reconcile 的做法是「跳过并报告」，导出应当一致。
- **未实测**：文件符号链接会被 `copyFileSync` 跟随、把存储之外的文件内容带进导出目录——只来自读代码，本机无权限创建文件符号链接。

### U-13（P3）`revisionsBumped` 口径

`inspection.changed` 在身份字段回填时也为真，而回填不改变 revision 数字。复现（`ws2-meta.mts` C）：存量形状的文件首次 reconcile 报 `revisionsBumped=1`，但 revision 仍是 5。这个口径从 v0.6.0 身份回填时就是如此；本次的 `metadataHash` 让已经回填过的文件再被计一次。建议把 `identityBackfilled` 和 `revisionsBumped` 分开计。

### U-14（P3）增量 offset 未实现

`lastOffset` / `lastCompleteLineOffset` 恒写 0，`refineSessionBatch` 每次 wire 变化都从头解析整个文件。目标文档「wire 变大：从安全边界继续解析」没有落地，注释里的「reserved」应当如实写成未实现。

### U-16（P2，自审新增）`remember` 返回的 revision 可能立刻失效

`writeWithResult` 按传入的**原始** `content` 算 `contentHash`（`memory-store.ts:369`），而读回时正文经过 `parseFrontmatter` 规范化（`\r\n` → `\n`，去掉开头空行）。两者不一致时，下一次读取把这次写入判定为「外部修改」。

**复现**（`selfaudit-remember.mts`）：

```text
plain body                         remember returned revision 1; ... immediate follow-up write with expectedRevision=1: ok
body starts with one newline       remember returned revision 1; ... immediate follow-up write with expectedRevision=1: RevisionConflictError
body starts with two newlines      ... RevisionConflictError
body with CRLF line endings        ... RevisionConflictError
body with a blank line inside      ... ok
```

同进程里读路径因为身份缓存看不出来（`changed=false`），但 `writeWithResult` 不走缓存，于是「remember 之后马上带 `expectedRevision` 再写」这种最常见的连续操作会被拒；换一个进程读则会看到 revision 直接 +1。模型产出的正文以空行开头并不少见。

**建议修复**：写入前把正文规范化成解析后的形态（`content.replace(/\r\n/g, '\n').replace(/^\n+/, '')`），对规范化后的正文计算哈希并落盘。

### U-17（P2，自审新增）`remember` 接受裸文件夹

`sanitizeFolder` 只拒绝绝对路径、`..` 和非法字符，`decisions`、`knowledge/sub` 都原样放行。看板那侧的 `validateFolderPath` 是限制在 `memory/` 和 `notes/` 的，MCP 工具这侧没有。

**复现**（`selfaudit-barefolder.mts`）：

```text
remember(folder="decisions") -> success, file at <store>/decisions/bare-folder-entry.md
reconcile: synced=true; indexed entries containing the bare-folder entry: false
--export-data: bare-folder entry exported: false
bare-folder file still on disk (never reconciled, never backed up): true
```

条目写入成功、调用方拿到 success，但它不在任何索引树里：不进 `memoryIndexTree`、不被 reconcile 回填身份、不在 `--export-data` / `--backup-data` 范围内。目标文档 §6.6「key 和 folder」对 folder 的约束需要对照（见 §4）。

**建议修复**（需要你定）：要么拒绝并提示改成 `memory/<类别>`，要么把裸类别名自动映射到 `memory/<类别>`；另配一个 doctor 动作迁移存量。

### U-18（P3，自审新增）看板保存不裁剪 essence 历史

`pruneEssenceHistory` 只在 `organize_memories` 的 store 与 rollback 里调用；看板的 `storeEssenceContent` 每次保存都复制一份历史但从不裁剪。`docs/ARCHITECTURE.md:178` 写的是两个入口共享「history archive (`essence/history/`, last 10)」。

## 8. 升级路径（仓库代码 × v0.5.1 形态的数据）

v0.5.1 → 0.6.0 的迁移是源码行为的一部分。做法：取一份 v0.5.1 实例存储的**临时副本**（来源 C：19 个工作区、440 个记忆文件、52 个主题），用仓库的 `IndexDao.reconcileIndex` / `ThemeManager` / `MemoryStore` 跑首次 reconcile，比较前后，跑完删除副本。只输出计数。

- 440 个文件各被重写一次（补 `id` / `contentHash` / `metadataHash`）；正文零改动、零丢失，既有 revision 数字零变化（429 个原本没有 revision 字段的文件被写成 1），`id` 零变化、无重复 id；全部带上 `metadataHash`。
- 19 个工作区首次 reconcile 全部 `synced=true`、无 corrupt、无错误；52 个主题全部通过结构校验；3 个 essence 正文不变。
- 首次 reconcile 的 `revisionsBumped` 合计 442（440 个记忆 + 2 条速记），即 U-13 的口径在真实数据上的读数。
- 非空的 10 个工作区要到第三次 reconcile 才走检查点跳过（前两次全量，因为回填写盘发生在结构哈希计算之后）；另外 9 个空工作区的索引为空，按现有条件永远全量扫。

待发布源码**不会**自动处理、升级后会原样继承的：v0.5.1 写出的陈旧 refined 行（索引器只补缺失，U-01）、落在 `memory/` 之外的条目（U-17）。

refined SQLite 的迁移（`selfaudit-refined-migrate.mts`，合成的 v0.5.1 形态库，不涉及任何实例数据）：首次打开时 `user_version` 0→2、日志模式切到 WAL、补齐 freshness 列并建进度表；4 条旧行全部保留并标记为 `unknown` 新鲜度，其中一条列损坏的行在搜索时仍被报告而不是被隐藏；对旧行的 UPSERT 正常，再次打开是空操作。这一步没有问题。
